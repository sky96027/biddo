# 외부 의존성 장애 대응 (Graceful Degradation)

> **상태**: 미결정
> **작성일**: 2025-06-22

---

## 현황

Elasticsearch에만 CircuitBreaker + DB fallback이 적용되어 있다. 나머지 외부 의존성(Redis, Kafka)에는 장애 시 대응 전략이 없다.

| 외부 시스템 | 장애 대응 | 영향 범위 |
| --- | --- | --- |
| Elasticsearch | CircuitBreaker + DB fallback | 검색, 유사 상품 추천 |
| Redis (Lettuce) | 없음 | 최근 검색어, 경매 상태 전환, Refresh Token |
| Redis (Redisson) | 없음 | 입찰 분산 락 — **입찰 기능 전체 불가** |
| Kafka 브로커 | 없음 | 입찰 이벤트 발행 — 알림/검색 동기화/WebSocket 전파 중단 |

## 미비 사항

### 1. Redis 장애 시 입찰 불가

`RedissonAuctionLock.executeWithLock()`에서 Redis 연결 실패 시 예외가 그대로 전파된다. Redis가 다운되면 입찰 기능 전체가 중단된다.

- 분산 락 자체를 우회할 수는 없음 (동시성 보장이 목적)
- 다만 연결 실패와 락 획득 실패를 구분해 사용자에게 다른 메시지를 제공해야 함
- Redis 복구까지의 임시 조치(예: 입찰 일시 중지 모드) 여부 검토

### 2. Redis 장애 시 경매 상태 전환 중단

`RedisAuctionLifecycle`이 TTL 기반으로 경매 상태를 전환한다. Redis가 다운되면 새 경매의 상태 전환 키가 설정되지 않는다.

- `AuctionLifecycleScheduler`(1분 주기)가 보완 역할을 하지만, 이 스케줄러가 Redis 장애를 인지하고 주도적으로 전환을 담당하는 구조는 아님
- Redis 복구 후 누락된 TTL 키를 복원하는 로직이 없음

### 3. Kafka 브로커 장애 시 이벤트 유실

입찰 시 `KafkaTemplate.send()`가 실패하면 이벤트가 유실된다. 입찰 자체(DB + Redis)는 성공하지만 후속 처리(알림, 검색 동기화, WebSocket, 인기 경매 집계)가 누락된다.

- 현재 이벤트 발행 실패가 입찰 트랜잭션을 롤백시키는지 여부 확인 필요
- 발행 실패한 이벤트의 재시도/보상 메커니즘 부재

## 검토 방향

| 대상 | 방향 |
| --- | --- |
| Redis 연결 실패 | 에러 분류 세분화 (연결 불가 vs 락 획득 실패), Health Check 연동 |
| Redis TTL 복원 | 스케줄러가 Redis 장애 복구 후 누락된 전환 키를 재설정하는 로직 추가 |
| Kafka 발행 실패 | Outbox 패턴 또는 재시도 큐 도입 검토 |
| 전반 | Resilience4j CircuitBreaker를 Redis/Kafka 어댑터에도 확대 적용 검토 |

## 선행 조건

- 각 장애 시나리오의 실제 동작을 Testcontainers로 검증 (컨테이너 중지 → 복구 시 동작 확인)
- 장애 빈도와 영향도 기반으로 우선순위 결정 (Redis 분산 락 > Kafka 이벤트 > Redis TTL 순으로 영향이 큼)
