# 캐싱 재검토

> **상태**: 미결정
> **작성일**: 2026-06-19

---

## 현황

Redis를 사용 중이나 **캐싱 목적의 사용은 없다**. 현재 Redis 용도는 모두 데이터 저장소 역할이다.

| 용도 | 구현체 | Redis 자료구조 | 성격 |
| --- | --- | --- | --- |
| JWT Refresh Token | `RefreshTokenRepository` | String (TTL 14일) | 인증 저장소 |
| 경매 상태 전환 타이머 | `RedisAuctionLifecycle` | String (TTL) | 이벤트 트리거 |
| 최근 검색어 | `RecentSearchRepository` | List (per user) | 사용자 데이터 |
| 인기 경매 랭킹 | `PopularAuctionRepository` | Sorted Set (TTL 1h) | 집계 데이터 |
| 입찰 분산 락 | `RedissonAuctionLock` | Redisson RLock | 동시성 제어 |

`@Cacheable` / `@CacheEvict` 등 Spring Cache 추상화를 사용하는 곳이 없고, HTTP 캐싱(`Cache-Control`, `ETag`) 설정도 없다.

## 캐싱 도입 후보

### 1. 카테고리 목록

**현재**: `GET /api/v1/categories` 호출 시마다 DB 조회 (`CategoryRepository.findAllByOrderBySortOrderAsc()`).

**문제**: 카테고리는 시드 데이터로 관리되며 런타임에 변경되지 않는다. 매 요청마다 DB를 조회할 이유가 없다.

**방향**:
- `@Cacheable`로 애플리케이션 레벨 캐싱 (Redis 또는 로컬 캐시)
- 카테고리 변경 빈도가 사실상 0이므로 TTL 길게 설정 (예: 24h) 또는 애플리케이션 시작 시 로딩
- 로컬 캐시(`Caffeine`)로도 충분할 수 있음 — Redis 네트워크 비용 불필요

### 2. 경매 상세 조회

**현재**: `GET /api/v1/auctions/{id}` 호출 시마다 DB 조회 (fetch join 포함).

**문제**: 인기 경매의 경우 동일 데이터를 반복 조회한다. 입찰이 발생하면 현재가가 변경되지만, 조회 빈도 대비 변경 빈도가 낮다.

**방향**:
- Redis 캐싱 + Kafka 이벤트 기반 무효화
- `bid-events` 토픽을 이미 소비하는 Consumer Group이 5개 존재하므로, 캐시 무효화용 Consumer를 추가하거나 기존 Consumer에서 처리
- 캐시 키: `auction:{id}`, 입찰/수정/상태 변경 시 evict
- 주의: 캐시와 DB 간 정합성 허용 범위 정의 필요 (실시간 입찰 현황은 WebSocket으로 푸시되므로 캐시 지연이 사용자 경험에 미치는 영향은 제한적)

### 3. HTTP 캐싱

**현재**: 모든 API 응답에 캐시 관련 헤더가 없다. 브라우저/CDN 캐싱이 동작하지 않는다.

**방향**:
- 카테고리 목록: `Cache-Control: public, max-age=86400` (변경 없는 정적 데이터)
- 경매 목록/상세: `Cache-Control: no-cache` + `ETag` (조건부 요청으로 304 응답)
- 인증 필요 엔드포인트: `Cache-Control: private` 또는 `no-store`

## 우선순위

| 후보 | 효과 | 복잡도 | 우선순위 |
| --- | --- | --- | --- |
| 카테고리 캐싱 | DB 쿼리 제거 | 낮음 (`@Cacheable` 한 줄) | 높음 |
| HTTP 캐싱 | 네트워크 트래픽 감소 | 낮음 (헤더 설정) | 중간 |
| 경매 상세 캐싱 | DB 부하 감소 | 중간 (무효화 전략 필요) | 낮음 (측정 후 판단) |

## 선행 조건

- 경매 상세 캐싱은 실제 트래픽에서 DB 조회가 병목인지 측정 후 결정. 부하 테스트(K6) 결과가 필요하다.
- 카테고리 캐싱과 HTTP 캐싱은 측정 없이 도입 가능 — 복잡도가 낮고 부작용이 없다.
