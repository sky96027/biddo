# Saga 패턴 도입 검토

> **상태**: 폐기
> **작성일**: 2026-06-23
> **폐기 사유**: 단일 DB 모놀리식 구조에서 Saga는 `@Transactional`이 보장하는 원자성을 수동으로 재구현하는 셈이며, 도입 전제(DB 분리)를 충족하지 않음

---

## 1. Saga 패턴이란

서비스가 분리되어 각자 다른 DB를 가지면, 여러 서비스에 걸친 작업을 하나의 DB 트랜잭션으로 묶을 수 없다. Saga 패턴은 진짜 트랜잭션 대신 **보상 트랜잭션(Compensating Transaction)**으로 일관성을 흉내낸다.

### 1.1 두 가지 구현 방식

**Choreography(안무형)**: 중앙 통제자 없이 각 서비스가 이벤트를 듣고 반응한다.

```
Bid 서비스: "입찰 저장됨" 이벤트 발행
Auction 서비스: 이벤트를 듣고 가격 업데이트 시도, 실패 시 "실패" 이벤트 발행
Bid 서비스: 실패 이벤트를 듣고 자기 데이터 롤백
```

**Orchestration(지휘형)**: 중앙의 Saga Orchestrator가 순서를 관리한다.

```
[Saga Orchestrator] -- "입찰해" --> [Bid 서비스]
                    -- "가격 바꿔" --> [Auction 서비스]
                    -- (실패 시) "입찰 취소해" --> [Bid 서비스]
```

## 2. Biddo에 불필요한 이유

### 2.1 단일 DB에서의 무의미

Biddo는 단일 PostgreSQL을 사용한다. EC2가 2대여도 같은 DB를 바라보는 같은 애플리케이션의 수평 확장이다.

- 입찰 기록 생성 + 경매 가격 갱신 → `@Transactional` 하나로 원자성 보장
- 트랜잭션을 쪼개면 "입찰은 저장됐는데 경매 가격이 안 바뀌는" 상태가 가능해짐
- 이를 보상하려면 입찰 취소 로직을 별도로 구현해야 함 → DB 롤백이 해주는 것을 수동 구현

### 2.2 Biddo의 현재 구조가 이미 적절한 패턴 조합

| 영역 | 현재 패턴 | Saga 필요성 |
| --- | --- | --- |
| 입찰 (Bid + Auction) | 분산 락 + 단일 트랜잭션 | 없음 — 원자성 필수 |
| 즉시구매 (buyNow) | 분산 락 + 단일 트랜잭션 | 없음 — 입찰+SOLD 원자성 필수 |
| 경매 생성/수정/취소 | 단일 트랜잭션 | 없음 — 단일 도메인 |
| 경매 종료 → 채팅방 생성 | 단일 트랜잭션 | 없음 — 같은 DB |
| 알림, 검색 인덱싱 | Kafka 이벤트 (커밋 후 발행) | 없음 — 이미 Choreography |

정합성이 필수인 핵심 흐름은 단일 트랜잭션, 유실 허용 가능한 부수효과는 Kafka Choreography — 이 조합이 현재 규모에 적합하다.

### 2.3 Saga가 필요해지는 시점

Saga는 **서비스를 분리하고 DB도 분리할 때** 비로소 의미가 있다. 현재 Biddo에는 그 시점이 아니며, MSA 전환 자체도 폐기된 상태다(별도 문서 "MSA_전환.md" 참고).

## 3. 참고: 이전 프로젝트(이커머스)의 오케스트레이션 패턴

과거 이커머스 프로젝트에서 모놀리식 상태로 Orchestration Saga의 아이디어를 적용한 사례가 있다. MSA로의 물리적 분리는 하지 않았지만, 트랜잭션 경계를 도메인 단위로 쪼개고 보상 로직을 직접 구현한 패턴이다.

### 3.1 구조

`PaymentFacade`가 오케스트레이터 역할을 하고, 각 UseCase(재고 차감, 잔액 차감, 쿠폰 상태 변경, 주문 상태 변경, 결제 저장)가 분리된 트랜잭션 단위로 동작한다.

```java
// @Transactional 제거 → 각 도메인 서비스(@Transactional) 단위 커밋 + 보상 로직 유효
public long processPayment(long orderId) {
    try {
        재고 차감;        // 자체 트랜잭션, 커밋 즉시 락 해제
        잔액 차감;        // 자체 트랜잭션
        쿠폰 상태 변경;    // 자체 트랜잭션
        주문 상태 변경;    // 자체 트랜잭션
        결제 내역 저장;    // 자체 트랜잭션
        paymentEventProducer.send(new PaymentCompletedEvent(...));
    } catch (Exception e) {
        // 보상: 재고 복원 → 잔액 복원 → 쿠폰 복원 → 주문 상태 롤백
        throw e;
    }
}
```

### 3.2 Orchestration + Choreography 혼용

핵심 결제 흐름(재고/잔액/쿠폰/주문)은 실패 시 즉시 보상이 필요하므로 Orchestration으로, 결제 완료 후 알림 등 후속 처리는 실패해도 결제에 영향이 없으므로 Choreography(Kafka 이벤트 발행)로 분리했다.

### 3.3 모놀리식 상태에서 얻은 실익

| 이득 | 설명 |
| --- | --- |
| 락 점유 시간 단축 | 각 단계가 즉시 커밋되어 동시 접근이 많은 테이블의 락 해제가 빨라짐 |
| 부분 실패의 명확한 가시성 | 상태 추적 변수로 어느 단계에서 실패했는지 즉시 파악 가능 |
| 보상 실패의 격리 | 각 보상 작업이 독립적으로 시도되어 하나의 보상 실패가 다른 보상을 막지 않음 |
| UseCase 재사용성 | 각 UseCase가 독립적이라 다른 흐름에서도 재사용 가능 |

### 3.4 이커머스에서 가능했던 이유

이커머스의 결제 흐름은 **독립적으로 보상 가능한 단계**(재고, 잔액, 쿠폰, 주문)로 구성되어 있었다. 각 단계가 서로 다른 리소스를 다루므로 트랜잭션을 쪼개도 각각 롤백이 가능했고, 락 점유 단축이라는 실익이 있었다.

### 3.5 Biddo에 적용할 수 없는 이유

Biddo의 핵심 흐름(입찰)은 "입찰 기록 + 경매 가격 갱신"이 **하나의 원자적 단위**다. 쪼개면 보상 로직이 필요해지지만, 현재 `@Transactional`이 DB 롤백으로 동일한 보장을 제공하고 있다. 분산 락 + `TransactionTemplate` 설계(ISS-002)가 보장하는 강한 일관성을 약화시키는 트레이드오프이며, 입찰처럼 정합성이 핵심인 도메인에는 권장하지 않는다.

---

## 4. 결론

- Biddo는 단일 DB 모놀리식으로, Saga 패턴의 전제 조건(DB 분리)을 충족하지 않는다.
- 정합성 필수 영역은 단일 트랜잭션, 부수효과는 Kafka Choreography — 현재 패턴 조합이 적절하다.
- 향후 MSA 전환으로 DB가 분리되는 시점에 재검토한다.
