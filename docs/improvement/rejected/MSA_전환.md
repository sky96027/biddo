# MSA 전환 검토

> **상태**: 폐기
> **작성일**: 2026-06-23
> **폐기 사유**: 1인 개발 포트폴리오 프로젝트 규모에서 전면적 MSA 전환의 실익이 비용을 초과하지 않음

---

## 1. 배경 및 목적

Biddo는 `biddo-api`, `biddo-domain`, `biddo-infra` 3개 모듈로 구성된 모놀리식 구조다. 모듈화(코드 구조 분리)는 되어 있으나, 실행과 배포는 하나의 Spring Boot 애플리케이션으로 합쳐져 있다. 본 문서는 이 구조를 MSA로 전환할 경우의 기준, 순서, 실익을 검토한다.

전면 전환을 전제로 하지 않는다. 부분 적용이 합리적인 영역과 그렇지 않은 영역을 구분하는 것이 핵심 목적이다.

---

## 2. 모놀리식과 MSA의 정의

모놀리식은 여러 기능이 하나의 배포 단위로 합쳐진 구조다. Biddo는 코드는 레이어별로 잘 나뉘어 있지만, 실행 시 하나의 프로세스로 동작하고 배포 시 하나의 산출물로 나간다. **모듈화와 모놀리식은 서로 다른 축의 개념**이며, 둘은 동시에 성립할 수 있다.

MSA로 인정되기 위해서는 다음 5가지 조건을 충족해야 한다.

| 조건 | 설명 |
| --- | --- |
| 독립 배포 | 서비스 하나만 배포해도 다른 서비스에 영향 없음 |
| 독립 데이터 저장소 | 서비스별로 별도의 DB(또는 스키마)를 가짐 |
| 비즈니스 도메인 단위 분할 | 명확한 도메인 경계를 기준으로 서비스를 나눔 |
| 서비스 간 네트워크 통신 | REST, gRPC, 메시징 등으로 통신 |
| 독립적인 확장(Scaling) | 트래픽이 몰리는 서비스만 따로 확장 가능 |

일부만 충족하는 점진적 전환은 **Strangler Pattern**으로 부르는 것이 정확하다.

## 3. 분리 기준: 레이어가 아니라 도메인

### 3.1 레이어별 분리는 유효하지 않음

`biddo-api`, `biddo-domain`, `biddo-infra`를 각각 독립 서비스로 배포하는 방식은 성립하지 않는다. domain의 Service 메서드 하나가 내부적으로 Repository, Cache Port 등을 수십 번 호출하는데, 이를 레이어별로 분리하면 메서드 내부 호출 하나하나가 네트워크 호출이 되어 레이턴시가 폭증한다. 이런 상태를 **분산 모놀리식(Distributed Monolith)**이라 부르며, MSA가 의도한 이점 없이 운영 복잡도만 늘어나는 대표적인 안티패턴이다.

```
유효하지 않은 분리축: 레이어 (api / domain / infra)
유효한 분리축: 비즈니스 도메인 (Auction, Bid, Search 등)
```

### 3.2 도메인별로 자르면 레이어 구조는 각 서비스 내부에 남는다

도메인 단위로 세로로 자르면, 각 서비스는 자기 내부에 다시 작은 레이어드/포트-어댑터 구조를 가지게 된다.

```
[Auction 서비스]            [Bid 서비스]
├── auction-api/            ├── bid-api/
├── auction-domain/         ├── bid-domain/
└── auction-infra/          └── bid-infra/
```

서비스를 몇 개로 쪼갤 것인가(가로축)와 각 서비스 내부를 어떻게 정리할 것인가(세로축)는 독립적인 문제다. Biddo의 현재 레이어 구조는 이 작은 단위에 그대로 재사용 가능한 형태로 이미 갖춰져 있다.

### 3.3 도메인별 분리 적합도

**분리하기 좋은 도메인의 특징**: 다른 도메인이 결과만 필요로 함(단방향 의존), 트랜잭션 경계가 독립적, 실패해도 다른 도메인에 즉각적 영향이 적음.

Biddo에서 이 조건에 맞는 영역은 Search(검색), Notification(알림), 이미지 처리다.

**분리하기 어려운 도메인의 특징**: 여러 도메인과 강한 트랜잭션 의존 관계를 가짐, 강한 데이터 일관성(ACID)이 요구됨.

Auction과 Bid가 이 영역에 해당한다. Auction은 Bid, Chat, Notification, Review, Report 등 거의 모든 도메인과 FK 관계를 가지므로, 분리 시 다음 문제가 발생한다.

1. 데이터 정합성 붕괴: 같은 트랜잭션으로 묶여 있던 입찰 저장과 가격 업데이트가 네트워크 호출로 바뀌어 원자성을 보장할 수 없게 된다.
2. FK 조회가 네트워크 호출로 바뀜: JOIN 한 번으로 끝나던 조회가 서비스 간 API 호출로 대체되어 레이턴시와 장애 전파 가능성이 증가한다.
3. 이벤트 스키마 관리 부담 증가: 서비스 간 계약(contract) 관리가 추가된다.

## 4. 인프라 분리 범위

MSA 전환 시 모든 인프라를 서비스별로 독립시키는 것은 아니다.

| 인프라 | 일반적인 처리 방식 |
| --- | --- |
| 애플리케이션 서버 | 서비스별로 독립 배포 (거의 필수) |
| DB | 이상적으로는 서비스별 독립 DB. 초기에는 스키마만 분리하는 절충안도 흔하다 |
| Redis | 공유 클러스터를 키 네임스페이스로 논리적으로 구분하는 경우가 많다 |
| Kafka | 서비스 간 통신의 매개체이므로 공유가 기본값이다 |

DB를 완전히 독립시키는 순간 Saga 패턴이 필요해진다(별도 문서 "Saga_패턴_도입.md" 참고).

## 5. 저장소(레포) 구조: Mono-repo

도메인별로 서비스를 쪼개더라도, 소스코드 저장 위치(레포)는 배포 단위(서비스)와 무관하게 선택할 수 있다.

```
biddo/ (한 레포)
├── auction-service/
│   ├── auction-api/ auction-domain/ auction-infra/
├── bid-service/
│   ├── bid-api/ bid-domain/ bid-infra/
├── search-core-service/
│   ├── search-api/ search-domain/ search-infra/
└── shared/  (공통 이벤트 스키마, 공통 DTO)
```

**Mono-repo 장점**: 공통 코드 동기화가 쉽고, 한 PR로 여러 서비스를 동시에 수정할 수 있다.

**Multi-repo가 유리한 경우**: 팀이 나뉘어 서비스별로 소유 팀과 접근 권한을 분리해야 하는 조직 규모. 1인 개발에서는 이 이점이 거의 없다.

## 6. MSA 도입의 진짜 동기와 비용

MSA는 "자원이 풍부한 서비스가 쓰는 방식"이 아니다. 도입 이유는 자원이 아니라 **조직 규모와 운영 복잡도**다.

**MSA를 도입하는 일반적 이유**: 팀이 커져 한 코드베이스의 동시 작업 충돌이 심해질 때, 서비스별 트래픽 패턴 차이가 커서 독립 확장이 필요할 때, 장애 영향 범위를 제한해야 할 때.

**MSA의 비용**: 서비스 수만큼의 서버 운영, 모니터링·로깅·분산 추적 인프라 추가, 네트워크 레이턴시와 장애 전파 복잡도 증가, Kubernetes·서비스 메시 등 운영 지식 필요.

```
직원 1~5명 스타트업: 모놀리식
직원 10~50명, 사용자 급증: 일부 기능만 분리 시작
직원 100명+, 여러 팀: 본격적인 MSA
```

Biddo(1인 개발) 맥락에서 분리를 검토하는 동기는 트래픽이나 조직 규모가 아니라 search-core의 재사용성이며, 이는 일반적인 MSA 도입 사례와 동기 자체가 다르다.

---

## 7. 결론

1. **모놀리식 유지**: 강한 트랜잭션 의존성과 FK 관계로 인해 분리 비용이 분리 이득을 초과한다.
2. **Search 도메인만 부분 분리 검토 가치 있음**: 분리 적합도가 높고, 재사용성이라는 별도의 동기가 있다.
3. **Choreography 패턴은 이미 일부 적용 중**: Kafka 토픽 구조를 향후 확장 기반으로 활용 가능하다.
4. **레이어가 아닌 도메인 기준으로만 분리를 고려**: 레이어별 배포는 분산 모놀리식 안티패턴이다.
5. **저장소는 Mono-repo 유지**: 1인 개발 규모에서 Multi-repo 전환 이유 없음.
