# 분산 추적 도입 (Distributed Tracing)

> **상태**: 채택
> **작성일**: 2026-06-24

---

## 1. 배경 및 목적

현재 Biddo는 요청이 Controller → Service → Kafka → Consumer → Notification/WebSocket 으로 흐르지만, 장애나 지연 발생 시 원인을 파악하려면 EC2 두 대의 로그를 수동으로 뒤져야 한다.

본 개선안은 Micrometer Tracing + Grafana Tempo를 도입하여 단일 요청의 전체 흐름을 추적 가능하게 만드는 것을 목적으로 한다.

---

## 2. 현황 분석

### 2.1 현재 구조

| 항목 | 현재 상태 |
| --- | --- |
| 로그 형식 | 텍스트 기반 (logback 기본) |
| 요청 추적 | 없음 — 요청 간 상관 ID 부재 |
| Kafka 이벤트 추적 | 불가 — Producer → Consumer 연결 불가 |
| 모니터링 | Prometheus + Grafana (메트릭만) |

### 2.2 문제점

- 입찰 → Kafka → 알림 흐름에서 알림 미도착 시 어디서 끊겼는지 확인 불가
- EC2 2대에서 동일 요청의 로그를 수동 매칭해야 함
- Kafka Consumer 지연과 서비스 지연을 구분할 수 없음

---

## 3. 결정: Micrometer Tracing + Grafana Tempo

### 3.1 채택 근거

- **Spring Boot 3 네이티브 지원**: `micrometer-tracing-bridge-brave` 의존성 추가 + 설정만으로 HTTP, JPA, Redis, Kafka에 자동 계측 적용
- **기존 Grafana 통합**: Prometheus + Grafana를 이미 운영 중이므로, Tempo를 datasource로 추가하면 메트릭과 추적을 단일 UI에서 조회 가능
- **Exemplar 연동**: Prometheus 메트릭에서 Trace로 직접 점프 가능 (메트릭 → 추적 원클릭 전환)
- **Kafka 헤더 전파 지원**: Brave가 Kafka Producer/Consumer 간 Trace ID를 헤더로 자동 전파
- **구현 비용 낮음**: 코드 변경 없이 설정과 의존성 추가로 80% 동작

### 3.2 Tempo 선택 근거 (vs Zipkin)

| 항목 | Grafana Tempo | Zipkin |
| --- | --- | --- |
| 설치 | Docker 이미지 하나 + 기존 Grafana에 datasource 추가 | Docker 이미지 하나 + 별도 UI(9411 포트) |
| UI | 기존 Grafana에 통합 | 별도 UI 운영 |
| 메트릭 ↔ 추적 연동 | Exemplar로 Prometheus → Trace 직접 점프 | 불가 (별개 시스템) |
| 관리 포인트 | Grafana 하나 | Grafana + Zipkin 2개 |

이미 Prometheus + Grafana를 운영 중이므로, 별도 UI를 추가하는 Zipkin보다 기존 스택에 통합되는 Tempo가 적합하다.

## 4. 구현 계획

### 4.1 의존성 추가

```gradle
// biddo-api/build.gradle
implementation 'io.micrometer:micrometer-tracing-bridge-brave'
implementation 'io.zipkin.reporter2:zipkin-reporter-brave'  // Tempo는 Zipkin 호환 프로토콜 지원
```

### 4.2 설정

```yaml
# application.yml
management:
  tracing:
    sampling:
      probability: 1.0  # 시연용 전수 샘플링, 운영 시 0.1 권장
  zipkin:
    tracing:
      endpoint: http://tempo:9411/api/v2/spans  # Tempo의 Zipkin 호환 엔드포인트
```

### 4.3 Kafka Trace 전파

Kafka Producer/Consumer Factory에 Brave 계측 설정을 추가하여 Trace ID가 Kafka 헤더로 전파되도록 한다.

### 4.4 구조화된 로그

logback 패턴에 traceId, spanId를 포함시켜 로그와 추적을 연결한다.

```xml
<pattern>%d{HH:mm:ss.SSS} [%thread] [%X{traceId}-%X{spanId}] %-5level %logger{36} - %msg%n</pattern>
```

### 4.5 인프라

Docker Compose에 Tempo 컨테이너 추가 + 기존 Grafana에 datasource 설정.

```yaml
tempo:
  image: grafana/tempo:latest
  command: ["-config.file=/etc/tempo.yaml"]
  volumes:
    - ./tempo.yaml:/etc/tempo.yaml
  ports:
    - "3200:3200"   # Tempo API
    - "9411:9411"   # Zipkin 호환 수신
```

### 4.6 검증 항목

- [ ] HTTP 요청에 Trace ID가 자동 부여되는지 확인
- [ ] Kafka Producer → Consumer 간 Trace ID가 전파되는지 확인
- [ ] Grafana에서 Tempo datasource로 입찰 → 알림 전체 흐름이 하나의 Trace로 표시되는지 확인
- [ ] 로그에 traceId/spanId가 출력되는지 확인
- [ ] Prometheus Exemplar → Tempo Trace 점프 확인

## 5. 트레이드 오프

### 얻는 것

- 요청 단위 전체 흐름 시각화 (HTTP → DB → Redis → Kafka → Consumer)
- 장애/지연 구간 즉시 식별
- Kafka 발행 실패 시 traceId 기반으로 유실 구간 추적 가능 (별도 로깅/모니터링 장치 불필요)
- 로그 ↔ 추적 연결로 디버깅 효율 향상
- 시연 시 Grafana 단일 UI로 메트릭 + 추적 통합 시연

### 잃는 것

- Tempo 컨테이너 추가 운영 부담 (경미)
- 전수 샘플링 시 네트워크/저장소 부하 (시연 규모에서는 무시 가능)
- Kafka Producer/Consumer Factory 설정 커스터마이징 필요
