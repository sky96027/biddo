# 검색 개선안

> **상태**: 채택 / 부분 완료
> **작성일**: 2025-06-19
> **구현 현황**: 1단계(Nori) ✅ 완료 · 2단계(function_score) ✅ 완료 · 3단계(하이브리드 벡터 검색) ⏸️ 보류

## 1. 배경 및 목적

현재 Biddo의 검색 기능은 Elasticsearch의 `More Like This` 쿼리와 기본 키워드 매칭(`match`)을 기반으로 동작한다. 이는 빠르고 비용 효율적이지만, 다음과 같은 한계가 있다.

- 형태소 분석이 적용되지 않아 한국어 검색 정확도가 낮다 (예: "캠핑의자"와 "캠핑 의자"를 다르게 처리). 테스트로 검증 완료.
- 키워드 정확 매칭에 의존하므로 동의어/의미 기반 검색이 불가능하다 (예: "노트북"과 "랩탑"을 별개로 취급).
- 정적인 스코어링 방식(BM25 기본값)을 사용해, 비즈니스 맥락(입찰 수, 인기도)을 반영하지 못한다.

본 개선안은 검색 정확도와 추천 품질을 단계적으로 개선하는 방향을 제시한다. 전면 재설계가 아닌, 기존 ES 인프라를 확장하는 점진적 접근을 전제로 한다.

## 2. 현황 분석

### 2.1 현재 구조

| 항목 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 검색 방식 | ES `match` 쿼리 + `More Like This` | 동일 (유지) |
| 동기화 | Kafka CDC (`AUCTION_CREATED`, `AUCTION_ACTIVATED` 등) | 동일 (유지) |
| 장애 대응 | Resilience4j CircuitBreaker + DB Fallback | 동일 (유지) |
| 인덱스 매핑 | `standard` 분석기 (한국어 형태소 분석 미지원) | ✅ `nori_analyzer` (복합어 분리, 조사 제거) |
| 스코어링 | ES 기본 BM25, 커스텀 부스팅 없음 | ✅ `function_score` — 입찰 수(log1p) + 마감 임박(gauss decay) |

### 2.2 강점

CircuitBreaker 기반 DB Fallback과 Kafka CDC 동기화 구조는 검색 인프라의 가용성 측면에서 이미 견고하게 설계되어 있다. 이 부분은 유지한다.

### 2.3 개선이 필요한 영역

인덱스 매핑이 `standard` 분석기를 사용하고 있어 한국어 검색에 한계가 있다. Testcontainers 기반 통합 테스트(`StandardAnalyzerKoreanTest`)로 다음 문제를 확인했다.

| 검색어 | 기대 결과 | 실제 결과 |
| --- | --- | --- |
| "캠핑의자" | "캠핑의자 접이식 경량", "캠핑 의자 릴렉스체어" 모두 검색 | "캠핑의자 접이식 경량"만 검색됨. 띄어쓴 "캠핑 의자" 누락 |
| "캠핑 의자" | 위와 동일 | "캠핑 의자 릴렉스체어"만 검색됨. 붙여쓴 "캠핑의자" 누락 |
| "블루투스이어폰" | "블루투스이어폰 노이즈캔슬링", "무선 블루투스 이어폰" 모두 검색 | "블루투스이어폰 노이즈캔슬링"만 검색됨. 띄어쓴 변형 누락 |
| "캠핑의자를" | 조사 "를" 제거 후 "캠핑의자" 관련 결과 검색 | 결과 없음 (0건) |
| "기계식키보드" | "기계식키보드 적축", "기계식 키보드 청축" 모두 검색 | "기계식키보드 적축"만 검색됨. 띄어쓴 변형 누락 |

`standard` 분석기는 공백 기준으로만 토큰을 분리하므로, 띄어쓰기가 다르면 같은 상품을 찾지 못하고 조사도 제거하지 못한다. 또한 검색 결과 순위에 비즈니스 신호(입찰 수, 조회 수, 최근성)가 반영되지 않으며, 키워드 매칭만으로는 사용자의 검색 의도를 충분히 포착하지 못한다.

## 3. 개선 방향

### 3.1 형태소 분석기 적용 (Nori) ✅ 구현 완료

한국어 검색의 정확도를 높이기 위해 Elasticsearch Nori 분석기를 인덱스 매핑에 적용한다.

**현재 매핑** (`AuctionDocument.java`):

```java
@Field(type = FieldType.Text, analyzer = "standard")
private String title;
```

**개선 매핑:**

```json
{
  "title": {
    "type": "text",
    "analyzer": "nori_analyzer",
    "fields": {
      "keyword": { "type": "keyword" }
    }
  }
}
```

```json
{
  "settings": {
    "analysis": {
      "analyzer": {
        "nori_analyzer": {
          "type": "custom",
          "tokenizer": "nori_tokenizer",
          "filter": ["nori_part_of_speech", "lowercase"]
        }
      },
      "filter": {
        "nori_part_of_speech": {
          "type": "nori_part_of_speech",
          "stoptags": ["E", "J", "SC", "SE", "SF"]
        }
      }
    }
  }
}
```

`title`은 형태소 분석된 `text` 타입으로 일반 검색에 사용하고, `title.keyword`는 정확 매칭(정렬, 집계)에 사용한다.

**구현 내용** (`AuctionDocument.java`, `ElasticsearchConfig` — `auction-settings.json`):

- `title`: `@MultiField` — nori_analyzer(검색) + `.keyword` 서브필드(정렬/집계)
- `description`: nori_analyzer 단독 적용
- 인덱스 설정: `nori_tokenizer` + `nori_part_of_speech(stoptags: E/J/SC/SE/SF)` + `lowercase` 필터

**검증**: `NoriAnalyzerKoreanTest` — "캠핑의자를" → 조사 제거 후 결과 반환, "블루투스이어폰" → "무선 블루투스 이어폰" 동시 검색 등 5개 케이스 통과.

**기대 효과**: "캠핑의자"와 "캠핑 의자"가 형태소 단위로 분리되어 동일하게 검색되며, 조사/어미가 제거되어 검색 정확도가 향상된다.

### 3.2 커스텀 스코어링 적용 ✅ 구현 완료

ES 기본 BM25 점수에 비즈니스 신호를 결합하는 `function_score` 쿼리를 적용한다.

```json
{
  "query": {
    "function_score": {
      "query": { "match": { "title": "캠핑 의자" } },
      "functions": [
        {
          "field_value_factor": {
            "field": "bid_count",
            "factor": 1.2,
            "modifier": "log1p"
          }
        },
        {
          "gauss": {
            "end_time": {
              "origin": "now",
              "scale": "3d"
            }
          }
        }
      ],
      "score_mode": "sum",
      "boost_mode": "multiply"
    }
  }
}
```

입찰 수가 높은 경매에 가중치를 부여하고, 종료 시점이 가까운 경매를 자연스럽게 상위 노출한다. `log1p` 모디파이어로 입찰 수 차이가 클 때 점수가 과도하게 벌어지는 것을 방지한다.

**구현 내용** (`AuctionSearchAdapter.buildQuery()`):

- `FunctionScore` 리스트: `FieldValueFactorScoreFunction(bidCount, factor=1.2, log1p, missing=0.0)` + `DateDecayFunction(endTime, origin=now, scale=3d)`
- `scoreMode=sum`, `boostMode=multiply`
- 정렬 정책 추가: 키워드 검색 + 명시적 정렬 없음 → `_score` DESC (relevance), 브라우징(키워드 없음) → `id` DESC (최신순)

### 3.3 하이브리드 검색 (벡터 + 키워드) ⏸️ 보류

> **보류 사유**: 임베딩 API(OpenAI 등) 호출 비용이 발생하는 구조이며, 포트폴리오 프로젝트의 운영 비용 범위를 초과. Kafka Consumer에 임베딩 API 호출 추가 및 `dense_vector` 필드 색인 구조는 설계 완료 상태로 유지하되, 실제 구현은 보류한다.

키워드 매칭만으로 포착하지 못하는 의미 기반 검색을 보완하기 위해, ES에 벡터 검색을 통합한다.

#### 왜 하이브리드인가

벡터 검색과 키워드 검색은 각각 강점이 다르다. 어느 한쪽만으로는 중고거래 검색을 충분히 커버하지 못한다.

| 검색어 | 키워드 검색 (BM25) | 벡터 검색 (kNN) |
| --- | --- | --- |
| "캠핑의자" → "캠핑 의자" | 형태소 분석으로 해결 | 해결 |
| "노트북" → "맥북 프로 M3" | **매칭 불가** (단어가 다름) | 의미적 유사도로 검색됨 |
| "다이슨 V15" → "다이슨 V15" vs "다이슨 V12" | "V15" 토큰이 정확히 매칭되는 문서 우선 | V15와 V12를 유사하다고 판단, **구분 약함** |
| "아이폰 15 프로맥스 256GB" | 모델명/용량 정확 매칭 | 스펙 차이 구분 약함 |

- **키워드 검색**: 모델명, 용량, 버전 등 정확한 키워드가 중요한 검색에 강함
- **벡터 검색**: 동의어, 유의어, 상위/하위 개념 등 의미적 연결이 필요한 검색에 강함

중고거래에서는 두 유형이 모두 빈번하므로, 둘을 결합하는 하이브리드 구조가 적합하다.

#### ES 통합 구조

벡터 저장소를 별도로 두지 않고, ES에 `dense_vector` 필드를 추가해 키워드 검색과 벡터 검색을 단일 엔진에서 처리한다.

**인덱싱 흐름:**

```
경매 등록/수정
  → Kafka CDC (기존 파이프라인)
  → Consumer에서 임베딩 API 호출 → 벡터 생성
  → ES 문서에 텍스트 필드 + 벡터 필드 함께 색인
```

**검색 흐름:**

```
검색 요청
  → 검색어를 임베딩 API로 벡터 변환
  → ES 단일 쿼리로 키워드(BM25) + kNN 동시 실행
  → RRF로 두 순위를 결합해 최종 결과 반환
```

**인덱스 매핑:**

```json
{
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "nori_analyzer",
        "fields": { "keyword": { "type": "keyword" } }
      },
      "description": {
        "type": "text",
        "analyzer": "nori_analyzer"
      },
      "title_vector": {
        "type": "dense_vector",
        "dims": 1536,
        "index": true,
        "similarity": "cosine"
      }
    }
  }
}
```

**검색 쿼리 (ES 8.x):**

```json
{
  "knn": {
    "field": "title_vector",
    "query_vector": [0.12, 0.45, "..."],
    "k": 10,
    "num_candidates": 50
  },
  "query": {
    "function_score": {
      "query": { "match": { "title": "캠핑 의자" } },
      "functions": [
        {
          "field_value_factor": {
            "field": "bid_count",
            "factor": 1.2,
            "modifier": "log1p"
          }
        },
        {
          "gauss": {
            "end_time": { "origin": "now", "scale": "3d" }
          }
        }
      ],
      "score_mode": "sum",
      "boost_mode": "multiply"
    }
  },
  "rank": {
    "rrf": {}
  }
}
```

`rrf` (Reciprocal Rank Fusion)가 BM25 순위와 kNN 순위를 자동으로 결합한다. 점수 정규화를 직접 구현할 필요가 없다.

#### pgvector 대신 ES 통합을 선택하는 이유

벡터 저장소로 pgvector(PostgreSQL 확장)를 사용하는 방법도 있다. 하지만 Biddo의 구조에서는 ES 통합이 더 적합하다.

| 관점 | ES 통합 | ES + pgvector |
| --- | --- | --- |
| 검색 경로 | ES 단일 쿼리 | ES → 임베딩 API → PG, 세 곳 왕복 |
| 점수 결합 | ES 내부에서 RRF 처리 | 애플리케이션 레벨에서 직접 구현 |
| 인덱싱 | 기존 Kafka CDC에 벡터 필드 추가 | ES + PG 양쪽에 동기화 필요 |
| 인프라 | 추가 구성 없음 | pgvector 확장 설치 필요 |

ES가 이미 검색 쿼리를 전담하고 있으므로, 벡터 검색도 같은 엔진에서 처리하는 것이 검색 경로를 단순하게 유지한다.

#### 임베딩 모델 선택 시 고려 사항

임베딩 모델은 검색 대상에 따라 달라진다. 텍스트 기반 검색(상품명, 설명)에는 텍스트 임베딩 모델(예: OpenAI text-embedding 계열)을 사용한다. 저장 시와 검색 시 반드시 동일한 임베딩 모델을 사용해야 벡터 공간이 일치해 유사도 비교가 의미를 가진다.

### 3.4 인기 검색어 다양성 (참고)

현재 `auction:popular` Sorted Set(1시간 TTL, 입찰수+조회수 기반)은 실시간 트렌드를 반영하는 구조다. 추천 검색어에도 동일한 패턴을 적용해 일정 주기로 갱신되는 인기 검색어 풀을 구성하고, 노출 시 일부를 무작위로 섞는 탐색적 요소를 추가하면 정적인 추천에서 벗어날 수 있다. 이는 우선순위가 낮은 개선 사항으로, 검토 대상으로만 남겨둔다.

## 5. 향후 검토 사항

### 5.1 자동완성 개인화

검색창 입력 중 추천 검색어에 개인화를 적용하는 방향도 검토 대상이다. 예를 들어 "전기자전거"를 검색한 이력이 있는 사용자가 "스로틀"을 입력 중일 때, "스로틀 전기자전거"처럼 과거 검색과 연관된 자동완성 후보를 우선 노출하는 방식이다.

이는 3.3의 검색 결과 재정렬과는 다른 문제다. 자동완성은 타이핑마다 호출되므로 응답 속도가 핵심이며, 매 입력마다 임베딩 API를 호출하는 구조는 비용과 지연 면에서 부적합하다. 따라서 다음과 같은 별도 구조가 필요하다.

```
1. Prefix 매칭: ES의 completion suggester 등으로 빠른 자동완성 후보 추출
2. 개인화 재정렬: 사전에 계산된 연관 키워드 매핑(Redis 캐시)을 사용해
   사용자의 최근 검색 이력(search:recent:{memberId})과 겹치는 후보를 우선 노출
```

연관 키워드 매핑은 실시간 계산이 아니라, 다수 사용자의 검색 패턴을 배치로 집계해 사전에 구축해야 한다. 일정 규모 이상의 검색 로그 데이터가 누적되어야 하므로, 현재 시점에서는 검토 대상으로만 남겨둔다.

## 6. 결론

1단계(Nori 형태소 분석기)와 2단계(function_score 커스텀 스코어링)를 구현 완료하여, 한국어 검색 정확도 개선과 비즈니스 신호 반영을 달성했다. CircuitBreaker 기반 가용성 설계는 그대로 유지된다.

3단계(하이브리드 벡터 검색)는 임베딩 API 비용 문제로 보류 상태이며, 설계 문서(§3.3)는 향후 도입 시 참고용으로 유지한다.
