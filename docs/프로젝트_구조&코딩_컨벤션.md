# 프로젝트 구조

## 멀티 모듈 구성

본 프로젝트는 관심사 분리와 의존성 관리를 위해 **멀티 모듈** 구조를 채택합니다.

```jsx
biddo/
├── biddo-api/              # API 모듈 (Controller, DTO, 인증/인가)
│   └── src/main/java/com/biddo/api/
│       ├── auction/           # 경매 API
│       ├── bid/               # 입찰 API
│       ├── member/            # 회원 API
│       ├── chat/              # 채팅 API
│       ├── notification/      # 알림 API
│       ├── search/            # 검색 API
│       ├── review/            # 후기 API
│       ├── report/            # 신고 API
│       ├── admin/             # 관리자 API
│       └── common/            # 공통 (응답 포맷, 인터셉터 등)
│
├── biddo-domain/           # 도메인 모듈 (Entity, Service, Repository)
│   └── src/main/java/com/biddo/domain/
│       ├── auction/           # 경매 도메인 [포트/어댑터]
│       │   ├── model/          # 순수 도메인 모델 (JPA 어노테이션 포함)
│       │   ├── port/out/       # AuctionRepository, AuctionSchedulePort, SearchIndexPort
│       │   ├── service/        # 비즈니스 로직 (포트 인터페이스에 의존)
│       │   └── exception/
│       ├── bid/               # 입찰 도메인 [포트/어댑터]
│       │   ├── model/
│       │   ├── port/out/       # BidRepository, BidEventPublisher, AuctionCachePort
│       │   ├── service/
│       │   └── exception/
│       ├── member/            # 회원 도메인 [레이어드]
│       ├── chat/              # 채팅 도메인 [레이어드]

├── biddo-infra/            # 인프라 모듈 (외부 시스템 연동 + 포트 구현체)
│   └── src/main/java/com/biddo/infra/
│       ├── auction/           # Auction 포트 구현체 (AuctionRepositoryImpl 등)
```

## 모듈 간 의존성

```jsx
biddo-api → biddo-domain
biddo-api → biddo-infra
biddo-infra → biddo-domain
```

- `biddo-api`: Controller, DTO, 인증/인가, API 응답 포맷. domain과 infra 모듈에 의존.
- `biddo-domain`: Entity, Service, Repository 인터페이스. 외부 의존성 없음 (순수 도메인 로직).
- `biddo-infra`: Kafka, Redis, Elasticsearch, S3, WebSocket 등 외부 시스템 연동. domain에 의존.

> **[Search 도메인 구조]** 검색은 ES(외부 시스템)와 Redis(최근 검색어) 의존이 있어 포트 인터페이스로 추상화합니다. KeywordAlert 엔티티는 레이어드 패턴으로 관리합니다.
>

> - **`biddo-domain/search/`** — `AuctionSearchPort`, `RecentSearchPort` (포트 인터페이스), `KeywordAlert` (엔티티), `SearchService`, `KeywordAlertService`
>

> - **`biddo-infra/elasticsearch/`** — `AuctionSearchAdapter` (ES + CircuitBreaker + DB fallback), `AuctionDocument`, Kafka CDC Consumer
>

> - **`biddo-infra/redis/`** — `RecentSearchAdapter` (Redis List 기반 최근 검색어)
>

> - **`biddo-api/search/`** — `SearchController`, `KeywordAlertController`, DTO
>

## 도메인별 패키지 구조 (상세)

### 아키텍처 전략: 복합도 기반 선택적 적용

Bid와 Auction 도메인에는 **포트/어댑터 패턴**을 적용하고, 나머지 도메인은 **레이어드 패턴**을 적용합니다.

**선택 기준**: Bid/Auction은 Redis 분산 락, Kafka 이벤트 발행, 자동 입찰 연쇄 처리, 스나이핑 방지 등 외부 시스템 의존이 4~5개로 가장 많으면서 비즈니스 규칙도 가장 복잡합니다. 의존성 역전을 적용하면 비즈니스 로직을 프레임워크 독립적으로 테스트할 수 있고, 외부 시스템 교체 시 domain 코드 변경이 불필요합니다. 나머지 도메인(Member, Chat, Review 등)은 로직이 단순하므로 보일러플레이트를 늘리는 것보다 레이어드로 유지하는 것이 효율적입니다.

### Auction 도메인 (포트/어댑터)

**biddo-domain 내부:**

```jsx
auction/
├── model/           # 도메인 모델 (JPA Entity 포함)
├── port/out/        # 아웃바운드 포트 (순수 Java 인터페이스)
│   ├── AuctionRepository.java    # DB 접근 추상화
│   ├── AuctionSchedulePort.java  # Redis TTL 경매 종료 스케줄링 추상화
│   └── SearchIndexPort.java      # ES 동기화 추상화
├── service/         # 비즈니스 로직 (포트 인터페이스에만 의존)
└── exception/
```

**biddo-infra 내 구현체:**

```jsx
infra/auction/
├── AuctionJpaRepository.java       # Spring Data JPA (JpaRepository 상속)
├── AuctionRepositoryImpl.java      # AuctionRepository 포트 구현
├── RedisAuctionSchedule.java       # AuctionSchedulePort 포트 구현
└── ElasticsearchSearchIndex.java   # SearchIndexPort 포트 구현
```

### Bid 도메인 (포트/어댑터)

**biddo-domain 내부:**

```jsx
bid/
├── model/           # 도메인 모델 (JPA Entity 포함)
├── port/out/        # 아웃바운드 포트 (순수 Java 인터페이스)
│   ├── BidRepository.java        # DB 접근 추상화
│   ├── BidEventPublisher.java    # Kafka 추상화
│   └── AuctionCachePort.java     # Redis 추상화 (현재가, 분산 락)
├── service/         # 비즈니스 로직 (포트 인터페이스에만 의존)
├── exception/
└── event/           # 도메인 이벤트 (선택)
```

**biddo-infra 내 구현체:**

```jsx
infra/bid/
├── BidJpaRepository.java           # Spring Data JPA (JpaRepository 상속)
├── BidRepositoryImpl.java          # BidRepository 포트 구현
├── KafkaBidEventPublisher.java     # BidEventPublisher 포트 구현
└── RedisAuctionCache.java          # AuctionCachePort 포트 구현
```

### 기타 도메인 (레이어드 — Member, Category, Chat, Notification, Review, Report, Search)

```jsx
member/
├── entity/          # JPA Entity (Spring 어노테이션 직접 사용)
├── repository/      # Spring Data JPA Repository (직접 상속)
├── service/         # 비즈니스 로직
├── exception/
└── dto/             # 도메인 내부 DTO (선택)
```

### API 모듈 (모든 도메인 동일)

```
도메인명/
├── controller/      # REST Controller
├── dto/
│   ├── request/     # 요청 DTO (*Request)
│   └── response/    # 응답 DTO (*Response)
└── mapper/          # Entity ↔ DTO 변환
```

## 예외 처리

### 구조

**공통 예외 처리기** (`@RestControllerAdvice`) + **도메인별 ErrorCode enum** 방식을 채택합니다.

```
common/
├── exception/
│   ├── BusinessException.java          # 비즈니스 예외 (추상)
│   ├── ErrorCode.java                  # ErrorCode 인터페이스
│   └── GlobalExceptionHandler.java     # @RestControllerAdvice
│
도메인별/
├── exception/
│   ├── AuctionErrorCode.java           # enum implements ErrorCode
│   └── AuctionNotFoundException.java   # extends BusinessException
```

### ErrorCode 인터페이스

```java
public interface ErrorCode {
    int getStatus();
    String getCode();
    String getMessage();
}
```

> `int getStatus()` — domain 모듈의 spring-web 의존을 제거하기 위해 HttpStatus 대신 int 사용.

### 도메인별 ErrorCode enum 예시

```java
@Getter
@RequiredArgsConstructor
public enum AuctionErrorCode implements ErrorCode {
    AUCTION_NOT_FOUND(404, "AUCTION_001", "경매를 찾을 수 없습니다."),
    AUCTION_ALREADY_ENDED(400, "AUCTION_002", "이미 종료된 경매입니다."),
    SELF_BID_NOT_ALLOWED(403, "AUCTION_003", "본인 경매에 입찰할 수 없습니다.");

    private final int status;
    private final String code;
    private final String message;
}
```

### BusinessException

```java
@Getter
public class BusinessException extends RuntimeException {
    private final ErrorCode errorCode;

    public BusinessException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
    }
}
```

## 도메인 모델 책임 원칙

도메인 객체(Entity/Model)는 자신의 불변식을 스스로 보호합니다. 외부에서 잘못된 상태의 객체가 생성되는 것을 원천 차단하는 것이 목표입니다.

### 책임 분류

| 분류 | 위치 | 설명 |
| --- | --- | --- |
| 값 검증 | 엔티티/모델 생성자·메서드 | 객체가 유효하지 않은 상태로 존재할 수 없도록 보장 |
| 상태 전이 | 엔티티/모델 메서드 | 허용된 전이만 수행, 잘못된 전이는 예외 |
| 도메인 판단 | 엔티티/모델 메서드 | 객체 스스로 자기 상태에 대한 질문에 응답 |
| 단순 계산 | 엔티티/모델 메서드 | 자기 필드 기반 값 산출 |
| 외부 의존 검증 | 서비스 | DB 조회가 필요한 검증 (중복 체크, 존재 확인 등) |
| 인코딩 전 원문 검증 | 서비스 | 엔티티에 원문이 도달하지 않는 경우 (비밀번호 길이 등) |

### DTO의 역할

DTO(Request)는 **형식 검증만** 담당합니다. 비즈니스 규칙은 포함하지 않습니다.

| 허용 | 예시 |
| --- | --- |
| 필수값 확인 | `@NotNull`, `@NotBlank` |
| 형식 확인 | `@Email` |

| 금지 | 예시 |
| --- | --- |
| 범위 규칙 | `@Min(1000)`, `@Size(min=8, max=20)` |
| 비즈니스 규칙 | `@Positive`, `@Max(5)` |

## API 응답 공통 포맷

모든 API 응답은 `ApiResponse<T>` 래퍼로 통일합니다.

### 성공 응답

```json
{
  "success": true,
  "data": { ... },
  "error": null
}
```

### 에러 응답

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "AUCTION_001",
    "message": "경매를 찾을 수 없습니다."
  }
}
```

### 페이지네이션 응답

```json
{
  "success": true,
  "data": {
    "content": [ ... ],
    "nextCursor": "eyJpZCI6MTAwfQ==",
    "hasNext": true
  },
  "error": null
}
```

> `totalElements` 제거 — COUNT 쿼리 제거로 Cursor 페이지네이션 성능 이점을 유지합니다.
>

### Testcontainers 설정

- PostgreSQL, Redis, Kafka 컨테이너를 사용하여 실제 환경과 동일한 통합 테스트 수행.
- `@Testcontainers` + `@Container` 어노테이션 기반으로 관리.
- 테스트 간 데이터 격리를 위해 `@Transactional` 또는 `@Sql` 사용.

# Git 전략

## 브랜치 전략

| 브랜치 | 분기 기점 | 머지 대상 | 설명 |
| --- | --- | --- | --- |
| `main` | - | - | 프로덕션 배포 브랜치 |
| `develop` | `main` | `main` | 개발 통합 브랜치 |
| `feature/*` | `develop` | `develop` | 기능 개발 (member-auth, auction-crud, bid-system 등) |
| `fix/*` | `develop` | `develop` | 버그 수정 (bid-concurrency-bug 등) |
| `refactor/*` | `develop` | `develop` | 코드 리팩토링 (redis-config 등) |
| `hotfix/*` | `main` | `main`  • `develop` | 긴급 수정 (프로덕션 장애 대응) |

### 예상 feature 브랜치 목록

`feature/member-auth`, `feature/auction-crud`, `feature/bid-system`, `feature/realtime-websocket`, `feature/search-elasticsearch`, `feature/chat`, `feature/notification`, `feature/review-reputation`

### 브랜치 네이밍

- 기능: `feature/{도메인}-{기능}`
- 버그: `fix/{도메인}-{설명}`
- 리팩토링: `refactor/{대상}-{설명}`
- 긴급: `hotfix/{설명}`

## 커밋 메시지 컨벤션

### 형식

```
<type>(<scope>): <subject>

<body> (선택)
```

### 타입

| 타입 | 설명 | 예시 |
| --- | --- | --- |
| feat | 새로운 기능 추가 | `feat(bid): 자동 입찰 기능 구현` |
| fix | 버그 수정 | `fix(auction): 경매 종료 시간 계산 오류 수정` |
| docs | 문서 수정 | `docs(readme): API 명세 업데이트` |
| style | 코드 포맷팅, 세미콜론 누락 등 코드 변경 없음 | `style(member): 코드 포맷팅 적용` |
